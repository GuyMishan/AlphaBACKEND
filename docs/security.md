# Alpha security

How Alpha authenticates, authorizes and isolates tenants, how sensitive data is handled, and what is known to be open. Every control below names the code that implements it and the test that proves it; anything without such evidence is listed under residual risks.

## Threat model

**Assets.** Personal identity data (national IDs, contact details), employment and salary data, pension contributions and 006 report payloads, bank account details, payment-method tokens and billing records, payment evidence and feedback documents, the audit trail, data-protection and signing keys.

**Actors.** Anonymous internet clients; authenticated users with an organization membership (Admin, PayrollManager, OperationsAgent, Viewer) and/or per-employer grants (Owner, Admin, User, Viewer); referents (internal staff assigned to organizations/employers); platform admins; payment providers calling webhooks; the clearinghouse (TEST simulator only in this codebase); background jobs.

**Trust boundaries.** Browser ↔ API (all input untrusted, including organization/employer IDs); provider ↔ webhook endpoints; API ↔ PostgreSQL (one application role); API ↔ external providers (payments, OTP delivery, malware scanner, storage).

## Authentication and sessions

- Development: header scheme (`X-User-Id`, `X-Platform-Admin`) registered **only** when `ASPNETCORE_ENVIRONMENT=Development`. The Docker image sets `Production`.
- Other environments: JWT bearer. With `PrototypeAuth:SigningKey` set, Alpha issues and validates its own HS256 tokens (issuer `alpha-prototype`, audience `alpha-frontend`, lifetime validated, 1-minute skew, 12-hour expiry) after OTP verification. Otherwise `Authentication:Authority`/`Audience` are used.
- Every authenticated request passes `SessionActivityMiddleware`: the `alpha:session_id` claim must match a `UserSession` row of the same user that is not revoked, not expired (12 h absolute), not idle (30 min), the user must be active, and a platform-admin claim must still be backed by `users.IsPlatformAdmin`. Otherwise the session is revoked and the response is `401` with `X-Alpha-Session-Expired: true`. Tokens without a session claim are rejected, so external-authority tokens must also carry an Alpha session to be usable.
- OTP: 6-digit codes, 5-minute expiry, at most 5 attempts per challenge, per-user advisory lock against concurrent issuing, consumed atomically. A new code is sent at most once per 60 seconds and 5 times per hour per account (login) or e-mail address (registration). During cooldown and hourly limits the request for an existing account receives the same `200` body as a fresh request (the latest active challenge, or a random ID), and nothing is sent. Unknown national-ID/phone pairs return a generic `400 invalid_credentials` with no challenge. This intentionally exposes whether the *pair* matches an active account; the anonymous endpoint remains rate-limited (20/min per client). Registration responses remain neutral.
- **Mail gateway.** E-mail goes through a Google Apps Script web app (`integrations/google-apps-script/Code.gs`, deployed by hand) when `Otp:Email:AppsScript:Url` is set. The backend accepts only an `https://script.google.com/macros/s/.../exec` URL and a secret of at least 32 characters, sent in the body. The script compares the secret in constant time, accepts either a 6-digit code or an invitation link (`https://<host>/invite?token=<64 hex>` that also appears in the text), caps the body at 4 KB and logs no addresses, codes or links. `MailGatewayContractTests` fails when the backend sends a message type the script does not handle.

Employer status updates (`PUT /api/organizations/{organizationId}/employers/{employerId}/status`) accept users with employer-level access, including viewers. This is a deliberate exception to the usual manage-employer permission: only Active/Closed status is mutable through this endpoint; organization/employer access is validated on the server, and an audit record is written for a real status change.

## Authorization

- **Default deny.** `AuthenticationSetup` sets a fallback policy requiring an authenticated user. All business routes also declare `RequireAuthorization()`. Anonymous routes are exactly: `/health`, `/health/db`, the four OTP/registration routes under `/api/auth`, `GET /api/invitations/{token}`, the two payment-provider callbacks, and (Development only) the OpenAPI document. A test fails if this set changes.
- **Resource-level checks.** Every handler calls `IOrganizationAuthorization` (implemented only by `OrganizationAccessService`) for the specific organization/employer and capability (`CanViewOrganization`, `CanManageOrganization`, `CanAccessEmployer`, `CanEditEmployer`, `CanManageEmployerBilling`, `CanCreateEmployee`, `CanCreateReport`, `CanTransmitReport`, ...). Employer-level checks first verify that the employer belongs to the route organization.
- **Platform boundary.** `/api/platform/*` handlers require `ICurrentUser.IsPlatformAdmin`. Referents cannot manage customer billing and cannot receive customer memberships.
- **Not authorization:** browser-supplied organization/employer IDs, UI state, or the route alone.
- Background jobs run with no user and act only on explicit IDs from the database; they expose no endpoints.

## Tenant isolation

Organization-owned rows carry `OrganizationId` and, where relevant, `EmployerId`; child rows (products, contributions, attachments, feedback lines) are reached only through a parent that is filtered by both. Queries take both IDs from the route after authorization and filter by them again. Bulk operations (report employee selection, report creation with a selection) verify that every referenced employment ID belongs to the route employer and reject the whole request otherwise; 006 imports are created for the route employer only. File downloads (report attachments, feedback documents, external-case attachments, payment evidence) re-check the full ownership chain before decrypting.

Isolation is enforced in the application, not by PostgreSQL row-level security; see residual risks.

## Sensitive data

- **Encryption at rest (application level).** `AesDataProtectionService`: AES-256-GCM with a 32-byte key from `Security:DataProtectionKey`, a per-value random nonce and a **purpose string as associated data**, format `alpha:v1:` (strings) or `ALP\x01` (bytes). Lookups use HMAC-SHA256 hashes with separate purposes. Purpose strings and formats are a compatibility contract; changing them makes stored data unreadable. Key rotation is not implemented.
- Protected fields: user and person national IDs and phones, bank account numbers and holder IDs, report employee identifiers and contacts, report employer identifiers/contacts, transmission payloads and responses, report attachments, clearinghouse feedback XML, external-case attachments.
- **API responses** use explicit projections. Platform user endpoints return `PlatformUserResponse` (no ciphertext, hashes or external subject). Billing account responses use a safe projection.
- **Logs** contain identifiers, counts and status codes only. Concurrency conflicts log only the trace identifier.
- **Audit rows** store method, path, result, status, client IP and user agent for mutations and file/export reads; no request bodies.
- **Legacy backfill.** `SensitiveDataBackfill` (run in the background at startup by `SensitiveDataBackfillHostedService`, `Security:EnableSensitiveDataBackfill`, default on) encrypts any remaining legacy plaintext and refreshes lookup hashes with the same formats and purposes. It pages by Id in bounded batches (`Security:SensitiveDataBackfill:BatchSize`/`BlobBatchSize`), filters blob tables in SQL so encrypted payloads are never loaded, commits per batch, never rewrites values already in the protected format, holds a PostgreSQL advisory lock so only one instance runs, reports unprocessable rows by table and Id (never by value) while leaving them unchanged, never stops the host, and records `sensitive-data-backfill-v1` in `identity.data_fixes` only when the pass had no failures **and** an independent SQL recount finds no plaintext left in scope; otherwise it runs again on the next start. Delete that row to force a re-run. A row written in plaintext between the final recount and the marker would be missed; that needs a writer that stores plaintext, and every write path for the columns in scope encrypts before saving in both this version and the version it replaces (reviewed in A12.3), so rows written during a deploy overlap are already protected. The production plaintext count in [release.md](release.md#sensitive-data-backfill) is the independent check. Scope: people, payment accounts, report employer snapshots, report employees, report payment accounts, transmission payloads and responses, report attachments, feedback XML. Users, registration OTPs, documents and case attachments are written encrypted by all code paths and are not in scope.
- **Uploads** are size-limited (11 MB for documents and evidence, 21 MB for 006 files, 64 KB for webhooks). Document uploads (report attachments, payment evidence, resolution documents, external-case attachments) are scanned by the configured malware scanner, which fails closed when not configured, and are stored encrypted. 006 XML/Excel files are parsed and schema-validated, not malware-scanned.

## Financial integrity

Billing invariants (from the billing payment stress audit; regression tests in `tests/Alpha.Api.Tests/Billing`):

- A billing period has one deterministic payment identity; unique indexes are the final guard against concurrent runs.
- A payment method becomes active only after a provider callback verified server to server; a browser redirect is never proof. An older setup callback never replaces the latest method; duplicate callbacks are idempotent (payload-hash dedup; a concurrent duplicate gets `503` until the first finishes; unverifiable callbacks are recorded as failed and answered `401`).
- An explicit decline may be retried by policy. A timeout, cancellation, crash or unknown outcome, or a "success" without a transaction/refund identifier, is **ambiguous**: it moves to `ReconciliationRequired` and is never re-charged automatically. Stale `Charging/Processing` states are moved there by the recovery pass.
- Pending/ambiguous refunds keep reserving their amount; refund idempotency keys cannot be reused for another payment or amount. Refunded payments are never charged again for the same period.
- Direct one-off provider charges are disabled (`409 direct_provider_charge_disabled`); the Fake provider is off unless `Payments:AllowFakeProvider`. Suspended/cancelled accounts are never reactivated by a zero-value or manual run. Local cancellation is authoritative before provider cleanup.
- Raw callback bodies and card data are never stored; provider customer/token/mandate identifiers never leave the API (the browser gets booleans and masked card metadata).
- Entitlement limits are checked under the organization advisory lock.
- `Billing:AutomaticBillingEnabled` is false by default; enable it in production only after provider credentials, a sandbox run and a reconciliation procedure exist. No test calls a real provider.

## Input and API security

- SQL: EF Core LINQ, interpolated EF raw SQL (parameterized), and ADO.NET commands whose interpolations are constant fragments, clamped integers or generated parameter names; all user values are bound parameters.
- Mass assignment: requests bind to explicit records, never to entities.
- Security headers on every response: `nosniff`, `X-Frame-Options: DENY`, restrictive CSP, `Referrer-Policy`, `Permissions-Policy`, `Cache-Control: no-store`; HSTS outside Development.
- CORS is not configured, so browsers block cross-origin calls by default.
- Rate limiting (`RateLimitingSetup`): 20/min per client on the anonymous credential endpoints (`/api/auth/*` except `session` and `logout`, so a new auth endpoint is strict by default), 1200/min per authenticated user elsewhere (including session check and logout), 1200/min per client for other anonymous traffic. IPv6 clients are grouped by /64. A 429 carries `Retry-After`.
- **Client IP behind a proxy.** `ReverseProxySetup` (first middleware) applies `X-Forwarded-For`/`X-Forwarded-Proto` only when `ReverseProxy:Enabled=true`, only from `ReverseProxy:KnownNetworks`/`KnownProxies`, and consumes at most `ReverseProxy:ForwardLimit` rightmost entries, so values a client prepends are ignored. Enabling it without a trust boundary fails startup; `ASPNETCORE_FORWARDEDHEADERS_ENABLED` (trust-all) is logged as critical. Disabled, every request is attributed to the TCP peer. `ReverseProxy:DiagnosticRequestCount=N` temporarily logs the raw peer and forwarding headers of the next N requests to establish the platform topology. Covered by `ReverseProxySecurityTests` (trusted, spoofed, untrusted, IPv6, IPv4-mapped, per-client rate limits).
- **Client IP through the frontend server.** Browser traffic reaches the API through the Next.js route handler on Vercel, whose egress addresses are shared and change, so forwarded headers can only ever reveal Vercel. When `FrontendProxy:SharedSecret` (at least 32 bytes, checked at startup) is set, a request carrying exactly that value in `X-Alpha-Proxy-Secret` (compared in constant time) and one valid address in `X-Alpha-Client-IP` is attributed to that address; otherwise both headers are ignored. Both are removed before any later middleware. The secret authenticates the caller, not its network: whoever holds it can choose their rate-limit bucket and audit IP (not their identity or permissions), so it lives only in the server environments of Render and Vercel and is rotated on suspicion. Covered by `ReverseProxySecurityTests` (valid, wrong and missing secret, unparsable and IPv4-mapped address, per-user limits, short secret).
- Errors follow one contract ([architecture.md](architecture.md#error-handling)): RFC 9457 Problem Details with `errorCode` and `traceId` on every error response, never exception text, SQL, stack traces or provider messages.
- **Links in e-mails and provider callbacks** use configured base URLs only (`Frontend:BaseUrl` for invitations and payment return pages, `Payments:PublicApiBaseUrl` for provider callbacks). Request headers are caller-controlled and never build such a URL. `Payments:PublicApiBaseUrl` (when unset: `RENDER_EXTERNAL_URL`, which Render sets for every web service) must be an absolute `https` URL without credentials, query or fragment (`http` only for a loopback host); otherwise payment-method setup returns `503 PAYMENT_CALLBACK_NOT_CONFIGURED` before contacting the provider. An explicit invalid value is never replaced.
- **Critical configuration fails fast.** `StartupConfiguration` stops startup when `Security:DataProtectionKey` is missing or not 32 bytes, or (outside Development) when neither `PrototypeAuth:SigningKey` (at least 32 bytes) nor `Authentication:Authority` is set. Optional integrations fail closed per request instead. Messages name settings, never values.

## Residual risks and open decisions

1. **Client IP (release gate for per-user login limits).** Browser traffic gets per-user rate limits and audit IPs only after the frontend sends the attested address and `FrontendProxy:SharedSecret` is set on both sides ([release.md](release.md#client-ip-through-the-frontend)); until then all frontend users share the frontend server's buckets, as today. Direct calls to the Render URL are attributed per Render proxy address until forwarded-header trust is enabled after the diagnostic in [release.md](release.md#client-ip-behind-render) (Render does not document its proxy addresses or hop count; community reports say it appends to `X-Forwarded-For` without stripping client values). A leaked shared secret lets its holder pick rate-limit buckets and audit IPs; there is no separate per-proxy ceiling.
2. **Backfill completion in production.** The backfill is now bounded and safe, but whether production still holds legacy plaintext is unknown without a read-only check ([release.md](release.md#sensitive-data-backfill)). After the first clean run it records its marker and stops running.
3. **No database-level tenant isolation.** No RLS, and child/parent tenant consistency (for example `employments.OrganizationId` versus its employer's organization) is not enforced by composite foreign keys. Evaluate composite FKs and RLS against a sanitized production copy before changing the schema.
4. **Single privileged database role.** The application runs the schema initializers at startup, so its role needs DDL rights. Separating a migration role from a least-privilege runtime role (and revoking `UPDATE/DELETE` on `audit.audit_events` from the runtime role) requires an operational change.
5. **Audit append-only is application-enforced.** Raw SQL or `ExecuteUpdate/Delete` against `AuditEvents` is not blocked by the database (none exists in the code; enforced by review).
6. **No data-protection key rotation.** A single key encrypts all values.
7. **External-authority JWT mode is effectively unusable** without an Alpha session claim; only the prototype issuer works end to end.
8. **OTP delivery errors** are logged with the exception; an SMTP recipient failure can include the recipient email address.
9. **Search wildcards.** `%`/`_` in catalog search terms are not escaped (semantic/performance only; values are parameterized).
10. **Registration still reveals unregistered national IDs to their claimant.** A code arrives in the applicant's own inbox only when the national ID has no account, so an attacker who uses their own e-mail address learns whether an ID is registered. Kept by product decision (no "already registered" e-mail for now). Mitigations in place: 20 requests per minute per IP on `/api/auth`, at most one code per minute and 5 per hour per e-mail address. Recommended: alert on many registration requests per IP or for many distinct national IDs, and add bot protection to the public forms.
11. **Mail quota exhaustion.** Apps Script `MailApp` has a daily recipient quota. Per-IP (20/min), per-account and per-e-mail limits slow abuse, but many IPs requesting codes for many e-mail addresses can still exhaust it and block login codes for everyone. Mitigations: bot protection on the auth forms, a transactional mail provider with a higher quota, quota monitoring.
12. **Login OTP timing and delivery failures.** For an existing account the request waits for mail delivery (about a second through Apps Script) and returns `503` if delivery fails; for an unknown identity it answers at once with `200`. Response time, or a `503` during a gateway outage, can still reveal that a national ID and phone pair has an account. The fix is to answer `200` before sending and deliver in the background. No reliable background-job mechanism exists yet, and the code exists only as a hash, so restart-safe delivery needs a durable, encrypted outbox (a schema change). Recommended next step: a bounded in-process queue with a hosted worker (retries with backoff, failures logged by challenge ID only, drained on graceful shutdown); a crash loses at most the queued codes, and the user asks again after the 60-second cooldown. Not implemented in this release.
13. **Apps Script deployment drift.** The deployed gateway is updated by hand; the repository copy is authoritative. Redeploy it after every change to `Code.gs`.
14. Real provider integrations, production key management, infrastructure hardening and load behavior were **not** tested here; an external security review is still recommended before claiming production readiness.

## User access type transitions

The organization-scoped `PUT /api/organizations/{organizationId}/access/users/{userId}/type` operation changes between platform, organization and direct-employer access. Only platform administrators can grant or revoke the global platform-admin flag; organization administrators can change customer organization/employer access only. Organization-role transitions reject removal of the last organization administrator, and self-demotion from platform administration is forbidden. Employer grants are replaced transactionally within the selected organization only; unrelated organizations are not altered. The endpoint rejects foreign-employer IDs and checks user entitlements when creating a membership. A platform-admin promotion preserves existing scoped memberships for safe reversibility; therefore these types are effective access categories, not an exclusive global database discriminator.

## Legal document publishing

The legal-document API permits anonymous reads of active and historical published/archived versions only; drafts and writes require an authenticated platform administrator. Markdown is bounded and rejects raw angle brackets and dangerous URI schemes, and consuming UIs must render Markdown with HTML disabled and URL sanitization. Publishing preserves text, creator timestamps and reacceptance flag. No user-consent enforcement is introduced in this foundation stage.

## Employer legal agreement prerequisite

Type 7 is employer-wide and may be uploaded only by users permitted to edit the employer, using the existing PDF signature, size, malware-scan and encrypted persistence path. All report send and hybrid resume endpoints enforce the document gate after `CanTransmitReportAsync` authorization and before any provider call, returning a scoped 409 when absent. This is an evidence-presence gate; it is not a cryptographic signature verification system.

## Manufacturer inquiry email data handling (October 2026)

The reporting feedback external-case inquiry flow uses verified manufacturer/product recipient metadata maintained by platform admins. The browser cannot override the recipient; the backend re-resolves tenant ownership, product and official error code before dispatch. Subject/body are editable and require explicit user action and confirmation. The default split-code templates include employer and report references but never automatically embed an employee national ID, bank credentials or uploaded evidence. No case attachments are mailed. The existing OTP email provider configuration (`Otp:Email`) is reused for manufacturer inquiries. If configuration is absent the route returns an explicit error and sends nothing. Provider acceptance is recorded, but recipient delivery is not implied. The dispatch log contains user-authored message bodies and should be treated as sensitive operational data. Access is tenant scoped and restricted to authorized reporting users; protect exports and retention accordingly.

**Manufacturer mail test safeguard:** `ManufacturerMail:TestMode` defaults to true even if the reporting simulator flag is off. The server, not the browser, enforces all email destinations as `alphapensia@gmail.com` in test mode and includes the originally intended address in the message. Switching to production delivery requires an explicit configuration override. Do not send real employee personal data to the shared test mailbox.
