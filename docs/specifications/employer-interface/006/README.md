# Employer Interface — Version 006

This directory contains the official Employer Interface Version 006 specification files used by Alpha.

## Specification sources

Alpha uses three complementary official source groups:

1. `Employer interface V 6.xlsx` — the business/codebook specification. It is the source of truth for code meanings, field applicability, conditional business rules, employer-responsibility error codes, and other rules that are not fully expressed by the XSD alone.
2. The Version 006 XSD files — the structural/schema specification. They are the source of truth for XML structure, ordering, data types, allowed XML values, required/nillable elements, and final XML validation.
3. `docs/specifications/mislaka/` — the pension clearinghouse operational/system rules supplied for Version 6.0. These are the source of truth for clearinghouse-side validation overlays, operation/payment compatibility, changed mandatory-field rules, and later the feedback/status lifecycle.

No source replaces the others. A generated Employer Interface document must satisfy the workbook business rules, the clearinghouse operational rules that apply before transmission, and the matching official XSD.

### Precedence rule

- Use the workbook when deciding what a code means, when a field is business-relevant, and which conditional rule applies.
- Use the clearinghouse system rules when they add or change clearinghouse validation behavior for Version 6.0 (for example contact-mobile validation, operation/payment compatibility, or conditional bank fields).
- Use the XSD when deciding the exact XML shape, element order, type, cardinality, and whether an element must still be emitted as `xsi:nil`.
- If the workbook marks a field as not relevant but the XSD still requires its element positionally, Alpha emits the element as `xsi:nil` rather than inventing a value.
- Do not invent business labels or code meanings that are not present in the official specification.

## Official workbook

`Employer interface V 6.xlsx`

The workbook is used to initialize and maintain Alpha reference data for Employer Interface 006, including categories such as:

- receipt types (`SUG-TAKBUL`)
- operation codes (`SUG-PEULA`)
- employee status
- deposit status
- last-deposit indication
- refund reasons
- payment methods (`KOD-EMTZAI-TASHLUM`)
- account types
- contribution types (`SUG-HAFRASHA`)
- Section 14 status (`SEIF-ARBA-ESRE-LAOVED`)
- official employer-responsibility feedback/error codes
- previous-report reference rules and their official exception reasons

Reference values used by UI selects are persisted in database-backed reference-data tables; the frontend must not maintain duplicate hardcoded business option lists.

## Official schemas

| Document type | Official file | Interface type |
| --- | --- | --- |
| Current / regular employer report | `mimshak_maasikim_shotef_xsd_schema_006.xsd.xml` | `SUG-MIMSHAK = 12` |
| Negative employer report | `mimshak_maasikim_shliliim_xsd_schema_006.xsd.xml` | `SUG-MIMSHAK = 13` |
| Summary feedback | `mimshak_maasikim_mesakem_xsd_schema_006.xsd.xml` | Summary feedback (`14` / `18` according to the schema) |
| Annual summary feedback | `mimshak_maasikim_mesakem_shnati_xsd_schema_006.xsd.xml` | `SUG-MIMSHAK = 16` |

All four files declare Employer Interface XML version `006` and are copied into the API runtime output during build/publish.

## Runtime behavior

Incoming XML is validated against all four official schemas. Exactly one schema must match before the document is accepted. Current and negative documents are routed to report import; summary and annual-summary documents are routed to feedback ingestion.

Outgoing XML is report-type-aware:

- `ManualReportKind.Current` is built with the dedicated current-report Version 006 builder and must satisfy workbook rules and validate against the current-report XSD.
- `ManualReportKind.Negative` is built with the dedicated negative-report Version 006 builder and must satisfy workbook rules and validate against the negative-report XSD.
- Difference reports are not transmitted directly; they must first be materialized as a current or negative report.
- Summary and annual-summary documents are feedback documents and are ingestion-only in the current Alpha flow.

The current and negative schemas are not treated as the same XML with only a different `SUG-MIMSHAK`. They have different business rules, required/irrelevant fields, and allowed operation codes. For example, negative reports use `SUG-PEULA` values `5` or `6`, while current reports use the current-report operation-code set.

Before transmission, Alpha applies workbook-level validation/rules and then validates the generated bytes against the matching official XSD. Only the exact byte array that passed validation is hashed and passed to the transmission provider.

## Required application data

Version 006 requires data that older Alpha screens did not collect. Alpha therefore stores dedicated Employer Interface profile/metadata fields and fails closed when mandatory information is missing instead of inserting placeholder values.

Employee profile data includes birth date, gender, email, mobile and address details. Alpha currently requires these fields in employee creation/profile screens so reports do not depend on last-minute completion of missing employee data.

Section 14 is represented by the official `SEIF-ARBA-ESRE-LAOVED` code rather than a simple boolean. Codes that require an effective/cancellation date must also include `SEIF-ARBA-ESRE-TAHRIH-KNISA-LETOKEF`.

Employer Interface report-product metadata includes operation/status fields, official payment method, account types and previous-report reference information where applicable.

Recipient/provider identity remains externally configured under `EmployerInterface006` settings. A real clearinghouse transport is intentionally not connected yet; the current transmission provider remains the mock provider until production integration is required.

## Reference-data implementation

Official V6 code labels and allowed values are seeded into database-backed reference-data tables. The workbook is the documentation/source used to maintain these initializers; runtime screens read the resulting reference data through the backend APIs.

When any official source is updated in the future:

1. replace/add the official specification file under `docs/specifications/`,
2. compare the changed workbook/XSD/clearinghouse rules,
3. update the relevant reference-data initializer and validation/builder rules,
4. update/add tests,
5. validate generated current and negative XML against the corresponding official XSDs and clearinghouse pre-send rules.

Do not parse the XLS at runtime in production as a substitute for versioned application logic. The committed workbook documents the official source; Alpha's versioned DB seeds and code implement it deterministically.

## Deferred integration checks

The following items are intentionally deferred until the real clearinghouse integration/testing phase and must be re-verified against actual clearinghouse behavior before production transmission:

- Birth-date wire format: the clearinghouse rules document states `DD-MM-YYYY`, while the official Version 006 XSD declares `TAARICH-LEIDA` as `xsd:date`, which serializes as `YYYY-MM-DD`. Keep XSD-valid output for now and verify the accepted wire format during clearinghouse integration.
- Employee identifier type (`SUG-MEZAHE-OVED`): Alpha currently emits type `1`. Add/verify support for the other official identifier type when a real use case is introduced.
- Old pension fund subtype (`SUG-KEREN-PENSIA`): Alpha currently emits `xsi:nil`. Add/verify support for old-pension-fund cases when needed and during clearinghouse integration.

## Testing

`tests/Alpha.Api.Tests/EmployerInterface006XmlBuilderTests.cs` builds representative current and negative XML documents, applies workbook-derived business rules, and validates the results against these exact official XSD files. The tests run in CI.

## Rules

- Do not modify or relax the XSD files to make application output pass validation.
- Do not change official workbook values merely to fit the current application model.
- The application code and data model must conform to the official Version 006 specification, not the other way around.
- When workbook and XSD constraints interact, preserve the workbook's business meaning while still emitting XML that satisfies the official XSD structure.
